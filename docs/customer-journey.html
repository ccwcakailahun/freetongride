Where it can go wrong

Critical moments to design for

Passenger

No driver accepts

After 90 seconds without an offer, suggest raising the fare or switching to Keke or Okada, instead of a silent spinner.

Passenger

SMS code never arrives

Resend after 60 seconds, then offer email. Show the number clearly so typos are caught.

Driver

Signal drops mid-trip

Keep tracking in the foreground service, queue location points and send them when the connection returns.

Driver

Passenger pays cash, app says unpaid

Cash confirmation by the driver closes the ride; the admin sees who confirmed and when.

Admin

SOS during a trip

Alert is impossible to miss: banner, sound, and the ride's last known location on the map.

Admin

Orange Money payment stuck

Pending payments are re-checked by cron; the admin can re-check or force from the deposit page.

Before I build

Decisions I need from you

1 · Driver offers or instant match?

The current backend lets drivers send offers and the passenger picks one. Your Location mockup shows "Driver nearby, 3 min away", which reads more like Uber's instant match.

Recommendation: keep offers (the backend already supports it, and passengers in Freetown are used to negotiating), but pre-fill the offer at the estimated fare so most drivers just tap Accept.

2 · Rebuild inside the existing apps, or start fresh?

Flutter/Rider and Flutter/Driver already talk to the live API at passenga.dorwei.com.

Recommendation: replace the screens inside the existing apps and keep their API, Pusher and payment code. Faster, and nothing on the server changes.

3 · Admin panel

Monitoring needs a web panel. Options: restyle the current Laravel admin to the FreeTongRide look, or build a new Flutter Web admin.

Recommendation: restyle the Laravel admin and add the Live map and SOS banner. A new Flutter admin would mean rebuilding every page.

4 · Missing canvases 2–5, 11 and 20

Send them if they exist; otherwise I design them to match.
